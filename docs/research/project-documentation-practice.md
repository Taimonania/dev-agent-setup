# Project documentation practice: long-lived knowledge for humans and agents

Primary-source research for the `dev-agent-setup` template. Every claim below is tied to a source URL or a file path in this repo. Where I could not verify something, I say so.

**Scope**: how to structure a project's durable knowledge — decisions, architecture, learnings, vocabulary, conventions — so it stays accurate, is cheap to maintain, and is genuinely useful to coding agents. Tech-agnostic throughout.

---

## 0. The organising idea: append-only vs living

The single most useful distinction I found across the sources is not in any of them explicitly, but falls out of comparing them: **documentation artifacts split into append-only records and living descriptions, and they have completely different maintenance economics.**

| Class | Examples | Maintenance cost | Rots? |
|---|---|---|---|
| **Append-only records** | ADRs, learnings/postmortems, research notes | ~zero after writing. They are dated statements about a moment. | No — a 2023 ADR is still a true record of a 2023 decision |
| **Living descriptions** | `ARCHITECTURE.md`, `CONTEXT.md` glossary, `AGENTS.md`, coding standards | Ongoing. Must track reality. | Yes, constantly |

Nygard's original ADR post relies on exactly this property: "If a decision is reversed, we will keep the old one around, but mark it as superseded. (It's still relevant to know that it was the decision, but is no longer the decision.)" ([cognitect.com/blog/2011/11/15/documenting-architecture-decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)).

**Design consequence for the template**: push as much knowledge as possible into the append-only class, and keep the living class small enough that a human will actually re-read it. Every page you add to `ARCHITECTURE.md` is a page you have signed up to maintain forever; every ADR you add is free after the day you write it.

## 1. The doc types a project needs

Seven artifacts, each distinct because it answers a different question and has a different lifecycle.

| Artifact | Question it answers | Class | Audience |
|---|---|---|---|
| `README.md` | What is this and how do I run it? | Living (small) | Humans first |
| `AGENTS.md` / `CLAUDE.md` | What must an agent know on *every* turn? | Living (tiny) | Agents |
| `CONTEXT.md` | What do our words mean? | Living (slow-moving) | Both |
| `docs/ARCHITECTURE.md` | What are the moving parts and how do they talk? | Living | Both |
| `docs/adr/NNNN-*.md` | Why is it this way? | Append-only | Both |
| `docs/learnings/*.md` | What did we get wrong, and what changed as a result? | Append-only | Both |
| `docs/guides/*.md` | How do I perform task X? | Living | Humans, agents on demand |

### Why these are separate files, not sections of one doc

Software Engineering at Google, Ch. 10 (Documentation), free at [abseil.io/resources/swe-book/html/ch10.html](https://abseil.io/resources/swe-book/html/ch10.html): "a document should have, in general, a singular purpose, and stick to it." Google identifies five document types (reference, design documents, tutorials, conceptual documentation, landing pages) precisely because each needs a different treatment.

The agent-side argument is stronger. The installed `writing-for-agents` skill (`.agents/skills/writing-for-agents/SKILL.md`) frames every document as spending one of **two loads**:

> **Context load** is the cost of always-loaded material on the agent's window … **Cognitive load** is the cost on the human: which documents exist and when to reach for each.

A single monolithic `DOCS.md` maximises context load (an agent pulling in the glossary also pulls in the deployment runbook) and destroys the ability to point at one thing. Separate files with sharp names are **context pointers**: "The pointer's *wording*, not its target, decides when the agent reaches the material."

### Where Diátaxis helps, and where it does not

Diátaxis ([diataxis.fr](https://diataxis.fr/)) separates docs into tutorials (learning-oriented), how-to guides (task-oriented), reference (information-oriented) and explanation (understanding-oriented), generated by two axes: practical vs theoretical, and acquisition vs application of knowledge.

**It helps** for the `docs/guides/` bucket: it stops "how to run the test suite" (how-to) from being interleaved with "why we chose this test strategy" (explanation), which is the most common docs failure I'd expect a new project to hit.

**It does not fit** ADRs and learnings. Diátaxis is a framework for *product/user* documentation — the four modes are defined relative to a user's needs while using a product. An ADR is a historical record, not any of the four modes; the closest is "explanation", but explanation is meant to be kept current, whereas an ADR is deliberately frozen. Do not force it. The author himself argues against big-bang structural application: "don't try to work on the big picture. It's both unnecessary and unhelpful. Diátaxis is designed to guide small steps" ([diataxis.fr/how-to-use-diataxis](https://diataxis.fr/how-to-use-diataxis/)).

**Recommendation**: use Diátaxis as a *review question* for anything in `docs/guides/` ("is this one mode or two glued together?"), not as the directory structure.

## 2. ADRs: format comparison and recommendation

### The three candidate formats

**Nygard (2011)** — the original. Sections: Title, Context, Decision, Status, Consequences. His own constraints, quoted from [the post](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions):

- Scope: "architecturally significant" decisions: "those that affect the structure, non-functional characteristics, dependencies, interfaces, or construction techniques."
- Location: "We will keep ADRs in the project repository under `doc/arch/adr-NNN.md`."
- Numbering: "ADRs will be numbered sequentially and monotonically. Numbers will not be reused."
- Superseding: "If a decision is reversed, we will keep the old one around, but mark it as superseded."
- Length and style: "The whole document should be one or two pages long. We will write each ADR as if it is a conversation with a future developer. This requires good writing style, with full sentences organized into paragraphs. Bullets are acceptable only for visual style, not as an excuse for writing sentence fragments."

**MADR 4.0.0 (Sept 2024)** — [adr.github.io/madr](https://adr.github.io/madr/). Full template (fetched verbatim from [github.com/adr/madr `template/adr-template.md`](https://raw.githubusercontent.com/adr/madr/main/template/adr-template.md)) has YAML frontmatter (`status`, `date`, `decision-makers`, `consulted`, `informed`) and sections: Context and Problem Statement, Decision Drivers (optional), Considered Options, Decision Outcome, Consequences (optional), Confirmation (optional), Pros and Cons of the Options (optional), More Information (optional). Filenames: `NNNN-title-with-dashes.md`. Status vocabulary: `proposed | rejected | accepted | deprecated | … | superseded by ADR-0123`. MADR also ships a **minimal** and a **bare-minimal** variant; the minimal one is just Context and Problem Statement / Considered Options / Decision Outcome / (optional) Consequences.

**Matt Pocock's format** — installed in this repo at `.agents/skills/domain-modeling/ADR-FORMAT.md`. Radically lighter:

> ```md
> # {Short title of the decision}
>
> {1-3 sentences: what's the context, what did we decide, and why.}
> ```
> That's it. An ADR can be a single paragraph. The value is in recording *that* a decision was made and *why*, not in filling out sections.

Status frontmatter, Considered Options and Consequences are explicitly optional, "only when they add genuine value. Most ADRs won't need them." Location: `docs/adr/`, sequential `0001-slug.md`.

### The sources disagree — honestly

| Dimension | Nygard | MADR 4.0.0 | Pocock (installed) |
|---|---|---|---|
| Length | "one or two pages" | Variable, structurally encourages long | 1–3 sentences is fine |
| Bullets | Discouraged: "Bullets kill people" | Bullet-driven (options, pros/cons) | Unconstrained |
| Required sections | 5 | 4 required + 5 optional | 1 (a title and a paragraph) |
| Rejected options | Part of Context | First-class section | Optional |
| Frontmatter | None (Status is a section) | YAML, 5 fields | Optional status only |
| Location | `doc/arch/adr-NNN.md` | `docs/decisions/NNNN-*.md` | `docs/adr/NNNN-*.md` |
| Ceremony | Medium | **Heavy** | Very light |

Nygard and MADR genuinely conflict on writing style: Nygard wants prose paragraphs and explicitly rejects fragment bullets; MADR's core value proposition is a bulleted options/pros-cons matrix. Both are defensible; they optimise for different things (a conversation with a future developer vs. a defensible comparison of alternatives).

### Recommendation for the template

**Ship the Pocock-shaped ADR, with Nygard's numbering, immutability and superseding rules, and MADR's optional sections available when a decision was genuinely contested.**

Reasoning:

1. **Ceremony kills adoption in a new project.** A five-section template with a pros/cons matrix means an ADR is a 30-minute task, so it doesn't get written, so the knowledge is lost. A one-paragraph ADR gets written. This is the trade the installed skill already makes, and the template should be internally consistent with the skills it ships alongside.
2. **`docs/adr/` over `docs/decisions/` or `doc/arch/`** purely because the installed skills (`.agents/skills/domain-modeling/SKILL.md`, `.agents/skills/setup-matt-pocock-skills/domain.md`) hard-code `docs/adr/`. There is no technical merit to any of the three paths; consistency with your tooling wins. Flag this as an arbitrary choice.
3. **Keep Nygard's hard rules** because they are what makes ADRs append-only and therefore free: monotonic numbering, numbers never reused, superseded records kept and marked, never deleted or edited-in-place to reflect a new decision.

### Immutability rule, stated plainly

- An ADR is **immutable once accepted**, except for: fixing typos, and adding a `Superseded by ADR-NNNN` line.
- Changing your mind = a **new** ADR that says "supersedes ADR-0007", plus a one-line edit to 0007's status.
- Never delete an ADR. The record that you once believed X is the whole point.

### When is an ADR warranted?

The installed skill's three-part test is the sharpest gate I found in any source (`.agents/skills/domain-modeling/ADR-FORMAT.md`), and I'd ship it verbatim:

1. **Hard to reverse**: the cost of changing your mind later is meaningful.
2. **Surprising without context**: a future reader will wonder "why on earth did they do it this way?"
3. **The result of a real trade-off**: there were genuine alternatives and you picked one for specific reasons.

All three must hold. It also enumerates qualifying categories: architectural shape, integration patterns between contexts, technology choices carrying lock-in, boundary/scope decisions, deliberate deviations from the obvious path, constraints not visible in the code, and non-obvious rejected alternatives. Nygard's scope test is compatible but broader: decisions "that affect the structure, non-functional characteristics, dependencies, interfaces, or construction techniques."

### Ready-to-use ADR template

````markdown
---
status: accepted
date: 2026-08-30
---

# 0007. Communicate between services with events, not synchronous calls

Services need to react to each other's state changes. We chose asynchronous
events over synchronous request/response because a synchronous chain makes any
one service's downtime everyone's downtime, and we cannot guarantee uptime
across the components we don't own. The cost we accept is eventual consistency:
readers may briefly see stale data.

<!-- Optional. Delete the headings you don't need. -->

## Considered options

- Synchronous calls between services — rejected: couples availability.
- Shared database — rejected: couples schemas, no ownership boundary.

## Consequences

- Every consumer must be idempotent; duplicate delivery is expected.
- Debugging a flow now requires correlating across components.
````

Minimum viable version of the same file, which is a completely acceptable ADR:

````markdown
# 0007. Communicate between services with events, not synchronous calls

Services need to react to each other's state changes. We chose asynchronous
events over synchronous calls because a synchronous chain makes any one
service's downtime everyone's downtime. We accept eventual consistency.
````

### ADR index

Do not hand-maintain a table of contents — it is a living doc pretending to be an index and it will rot. Rely on the filename convention (`NNNN-kebab-title.md`), which makes `ls docs/adr/` a readable index for both humans and agents. Ship a short `docs/adr/README.md` explaining the rules instead (template in §7).

## 3. Architecture documentation

### The three candidates

**C4 model** ([c4model.com](https://c4model.com/)) — four hierarchical levels: System Context, Containers, Components, Code. Notation-independent and tooling-independent. Simon Brown's own scoping guidance, from [c4model.com/diagrams](https://c4model.com/diagrams): "you don't need to use all 4 levels of diagram; only those that add value - the system context and container diagrams are sufficient for most software development teams." (I could not find, on c4model.com, an explicit statement that code-level diagrams are discouraged; the [abstractions/code page](https://c4model.com/abstractions/code) only defines the term. Claims elsewhere that Brown "recommends against level 4" are not verifiable from his site as of this research.)

**arc42** ([arc42.org/overview](https://arc42.org/overview)) — a 12-section template: 1. Introduction & Goals, 2. Constraints, 3. Context & Scope, 4. Solution Strategy, 5. Building Block View, 6. Runtime View, 7. Deployment View, 8. Crosscutting Concepts, 9. Architectural Decisions, 10. Quality Requirements, 11. Risks & Technical Debt, 12. Glossary. The site says it is "tailorable to your specific needs" and notes that sections 5 and 8 are typically the most extensive and grow continuously. It also offers an "arc42 canvas" that "captures a whole system on a single page" for teams wanting something lighter than twelve sections.

**Single `ARCHITECTURE.md`** — one file, no framework.

### Comparison

| | C4 | arc42 | Single `ARCHITECTURE.md` |
|---|---|---|---|
| What it gives you | Shared vocabulary + diagram levels | An exhaustive checklist of what to document | Nothing but a place to write |
| Setup cost | Low (it's a way of thinking) | Medium-high (12 sections to seed) | Zero |
| Maintenance cost | Medium — diagrams drift; needs diagrams-as-code to survive | **High** — 12 sections is 12 things to keep true; overlaps ADRs (§9) and glossary (§12) | Low, if kept to one page |
| Agent-friendliness | Poor if the artifact is an image; good if text/DSL | Good (structured markdown) but bloats context | Good |
| Risk | Diagram tooling lock-in | Abandonment; half-empty sections are worse than none | Becomes a dumping ground |

**Honest flag: arc42 is heavyweight.** For a brand-new project of unknown size it is over-specified, and it duplicates artifacts the template already has as first-class files (its §9 Architectural Decisions is your ADR directory; its §12 Glossary is your `CONTEXT.md`). Adopting it would create two homes for the same meaning, which `writing-for-agents` calls out directly: "Keep each meaning in a **single source of truth** … **Duplication** … costs maintenance and tokens."

**Honest flag: image diagrams are an agent-hostile format.** An agent reads text far more cheaply than it reads a PNG, and cannot diff a PNG in review. If you draw, draw in a text DSL that lives beside the code.

### Recommendation

**One `docs/ARCHITECTURE.md`, structured with C4's first two levels as its section headings, capped at roughly one page, with any diagram written as text.**

- Borrow C4's *vocabulary* (system context → containers) because it gives you the two questions actually worth answering: what is outside the system, and what are the separately-deployable/runnable pieces inside it. Skip levels 3 and 4 — component and code structure is derivable from the codebase, and `writing-for-agents` is explicit that restating the environment is a **cache** that "earn[s] its load only when the lookup is expensive."
- Skip arc42 unless and until the project is large enough that someone asks for a specific missing section. If that happens, adopt only that section.
- Everything explanatory ("why is it this way") belongs in an ADR, not here. `ARCHITECTURE.md` describes the *present*; ADRs explain the *past*. That split is what keeps `ARCHITECTURE.md` short enough to stay true.

Also add an explicit **"Where things live"** section — the map from concept to directory. This is the single highest-value thing you can give a coding agent, and the installed `retro` skill treats it as a named category: "**Navigation**: how easy was it for the agent to find the right files? … Would a **navigation pointer** make it easier?" (`.agents/skills/retro/SKILL.md`).

## 4. Learnings and retros

### Primary source

Google SRE Book, "Postmortem Culture: Learning from Failure" ([sre.google/sre-book/postmortem-culture/](https://sre.google/sre-book/postmortem-culture/)). A postmortem is "a written record of an incident, its impact, the actions taken to mitigate or resolve it, the root cause(s), and the follow-up actions to prevent the incident from recurring." Their published trigger criteria:

- User-visible downtime or degradation beyond a certain threshold
- Data loss of any kind
- On-call engineer intervention (release rollback, rerouting of traffic, etc.)
- A resolution time above some threshold
- A monitoring failure (which usually implies manual incident discovery)

Plus: any stakeholder may request one. Blamelessness is the load-bearing cultural requirement — it "operates from the premise that everyone involved had good intentions", which is what stops incidents being hidden.

### Adapting this to a new, small, possibly solo project

Google's triggers assume production traffic and an on-call rotation. A day-one template has neither. Generalise the underlying principle — *write one when the system surprised you* — into triggers a new project actually hits:

Write a learning when **any** of these is true:

1. Something broke in a way nobody predicted (production or not).
2. You lost work or data, however briefly.
3. A fix took disproportionately long relative to its eventual size — the time went into *finding* it, and that search is the knowledge.
4. You or an agent made the same mistake twice.
5. An assumption held by the team or written in a doc turned out to be false.

Trigger 4 is also Anthropic's own trigger for updating `CLAUDE.md` — "Claude makes the same mistake a second time" ([code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory)) — which is the useful hint that a learning often has a follow-up action *in a steering file*.

**Do not write one for**: a bug you understood immediately, or anything where the fix is the whole story.

### Two distinct retro types — keep them apart

The installed `retro` skill (`.agents/skills/retro/SKILL.md`) is *not* an incident postmortem. It is explicitly about the **agent's environment**: "You are suggesting improvements to the coding agent's **environment** to improve future runs", scanning categories of navigation, automated checks, coding standards, `AGENTS.md` bloat, tool economy, no-ops, and information access. Its output lands in steering files, standards, and tooling — not in a narrative document.

So the template needs both, and should not conflate them:

- `docs/learnings/` — what the *system* taught us. Append-only, narrative, human-facing and agent-readable.
- The `retro` skill's output — what the *agent setup* should change. Lands as edits to `AGENTS.md`, `docs/CODING_STANDARDS.md`, hooks, or CI.

### Learning template

````markdown
# 2026-08-30 — Duplicate records after a retried request

**Trigger**: data loss / corruption

## What happened

A client retried a request after a timeout. The server had already committed the
first attempt, so the retry created a second record. Roughly 40 duplicates over
two hours before anyone noticed.

## Why it happened

We assumed a timeout meant the work had not happened. It meant we did not hear
back. The write path had no idempotency key, so the server could not tell a
retry from a new request.

## What we changed

- Write path now requires a caller-supplied idempotency key.
- Added a test for "same key twice = one record".
- Recorded the general rule in ADR-0011 (all state-changing endpoints are idempotent).

## The transferable lesson

A timeout is not a failure signal; it is an absence of information. Any retry
across a boundary we do not control needs an idempotency key.
````

Notes on the format:

- **The last section is the point.** Everything above it is context; "the transferable lesson" is the part a future reader or an agent can actually apply. Keep it to one or two sentences, stated as a rule.
- **Blameless**: describe systems and assumptions, never people. Enforce this in the template by giving it no field for "who".
- **Filename**: `YYYY-MM-DD-slug.md`. Dates, not sequence numbers — unlike ADRs, learnings are never cross-referenced by number, and the date is the most useful sort key.
- **Link outward, don't restate.** If the fix produced an ADR or a standard, link it. The installed `handoff` skill states the same discipline for its own artifact: "Do not duplicate content already captured in other artifacts (specs, plans, ADRs, issues, commits, diffs). Reference them by path or URL instead."

## 5. The human/agent split

### What the primary sources actually say

**AGENTS.md** ([agents.md](https://agents.md/)) is a convention, not a spec. Its own FAQ, on whether there is a formal specification: "No. AGENTS.md is just standard Markdown. Use any headings you like; the agent simply parses the text you provide." It mandates nothing. It suggests: build and test commands, code style guidelines, testing instructions, security considerations, commit/PR guidelines. Placement: repo root; "Place another AGENTS.md inside each package. Agents automatically read the nearest file in the directory tree, so the closest one takes precedence." And: "explicit user chat prompts override everything." Framing: "Think of AGENTS.md as a **README for agents**."

**CLAUDE.md** ([code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory)) — Anthropic's guidance, which is unusually concrete:

- **Claude Code reads `CLAUDE.md`, not `AGENTS.md`.** The documented interop is an import: a `CLAUDE.md` containing `@AGENTS.md` "so both tools read the same instructions without duplicating them", optionally followed by Claude-specific additions. A symlink also works.
- **Size**: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence."
- **Specificity**: "'Use 2-space indentation' instead of 'Format code properly'".
- **What to cut**: their `/doctor` trim check "cuts content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews, and keeps pitfalls, rationale, and conventions that differ from tool defaults." This is a strong, first-party statement that **an architecture overview does not belong in CLAUDE.md.**
- Load order: managed policy → user (`~/.claude/CLAUDE.md`) → project (`./CLAUDE.md` or `./.claude/CLAUDE.md`) → local (`./CLAUDE.local.md`, gitignored). Files are concatenated, not overridden. Imports use `@path`, max depth 4, and imported files load at launch — so imports organise but do **not** reduce context.
- `.claude/rules/*.md` with `paths:` frontmatter load only when Claude touches matching files. This is the one mechanism that genuinely reduces always-on context.

**The installed skills' answer.** `retro/SKILL.md` is blunt about the hierarchy:

> `CLAUDE.md`/`AGENTS.md`: these files are pushed to the context window of any agent working in this repo. They should be used **incredibly sparingly**, usually only for **navigation pointers** to other files.
> `CODING_STANDARDS.md`: this file is read during **review**, not implementation.

That second line is a genuinely non-obvious insight and I'd adopt it: standards enforcement belongs to the reviewing agent, which sees a diff and has no exploration burden, not the implementing agent, which is under "context pressure".

And `CONTEXT.md` is the Pocock answer to vocabulary (`.agents/skills/domain-modeling/CONTEXT-FORMAT.md`): a glossary and nothing else. "`CONTEXT.md` should be totally devoid of implementation details. Do not treat `CONTEXT.md` as a spec, a scratch pad, or a repository for implementation decisions."

### The rule that prevents duplication

**One meaning, one file. `AGENTS.md` holds pointers, never content.**

Concretely:

| Knowledge | Lives in | `AGENTS.md` contains |
|---|---|---|
| What the project is | `README.md` | nothing |
| Build/test/run commands | the project's own config (task runner, manifest) | the one command to discover them, only if non-obvious |
| Domain vocabulary | `CONTEXT.md` | one line: read this before naming things |
| System shape | `docs/ARCHITECTURE.md` | one line pointer |
| Why decisions were made | `docs/adr/` | one line: check these before contradicting them |
| Code conventions | `docs/CODING_STANDARDS.md` | one line, flagged as review-time |
| Past failures | `docs/learnings/` | one line pointer |
| Genuine always-on rules | `AGENTS.md` itself | the 3–8 rules that change behaviour every session |

`writing-for-agents` supplies the test for what stays in the always-loaded file: **is it a no-op?** "an instruction the model already obeys by default pays load to say nothing … When a sentence fails, delete the whole sentence rather than trim words from it." And on restating the environment: "Cache what the agent cannot find by looking: the unwritten convention, the reason behind a choice, the gotcha no config confesses. Leave the one-file, one-command lookups to the environment, where they cannot go stale."

### Which file to create

Write the content in **`AGENTS.md`** (the cross-tool convention, 60k+ repos per agents.md) and make **`CLAUDE.md`** a one-line import of it, per Anthropic's documented pattern. This gives Claude Code, and any AGENTS.md-reading tool, the same single source.

Note a conflict with the installed tooling: `setup-matt-pocock-skills/SKILL.md` says "Never create `AGENTS.md` when `CLAUDE.md` already exists (or vice versa)" and edits whichever exists. The import pattern satisfies this in spirit — there is exactly one file with content — but if you ship both files pre-created, that skill will pick `CLAUDE.md` and write its `## Agent skills` block there, above the import. That is fine, but be aware of it.

### Should the README be for humans or agents?

Humans. agents.md's own framing is that AGENTS.md exists precisely so you can "give AI agents the context they need without cluttering your README" and keep the README "concise and focused on human contributors". Don't agent-optimise the README; point at it from `AGENTS.md` if it's genuinely worth an agent's tokens (often it isn't — a README's install instructions are a lookup the agent can do).

## 6. Freshness: what actually stops rot

Ordered by cost-effectiveness for a small new project.

**1. Shrink the living set (free, highest impact).** Rot is proportional to the volume of living description. Four living docs of one page each will stay true; forty pages will not. This is the whole reason for the append-only/living split in §0.

**2. Docs beside the code, in the same PR (free).** Software Engineering at Google, Ch. 10: documentation should "Be placed under source control … Have clear ownership … Undergo reviews for changes." Their reported outcome after moving docs into source control: "The documents became better" because engineers filed bugs and reviewed docs with familiar workflows. A doc in a wiki has no review gate; a doc in the repo inherits the code's.

**3. A review checklist item, not a policy (free).** One line in your PR template beats a paragraph in a contributing guide:

> - [ ] If this changes a container, its interface, or where something lives, `docs/ARCHITECTURE.md` is updated.
> - [ ] If this reverses a decision recorded in `docs/adr/`, a new ADR supersedes it.
> - [ ] If this introduces or renames a domain term, `CONTEXT.md` is updated.

**4. Make the reviewing agent the enforcer (cheap, agent-specific).** Per `retro/SKILL.md`, standards belong to review, not implementation. Put "check the ADR/glossary/architecture gates above" into the review-time standards file rather than into `AGENTS.md`, where it would burn context on every turn including the ones that touch no docs.

**5. Automate only the mechanical checks (cheap).** In CI: broken relative links in `docs/`, ADR filename/numbering collisions, and `AGENTS.md` line count over its budget. These are the checks a linter can be right about. Do **not** try to automate "is this doc true" — nothing can.

**6. Freshness metadata (medium cost, defer).** Google's mechanism: `freshness: { owner: username, reviewed: '2019-02-27' }`, where "metadata in the documentation set will send email reminders when the document hasn't been touched in … three months", and updating the date requires a code review. This works, but it needs a bot and an owner roster. **Flag as heavyweight**: don't ship it in a day-one template. Ship the cheap version — a `Last reviewed: YYYY-MM-DD` line on living docs only — and let a project graduate to automation if it grows.

**7. Delete aggressively (free, underused).** `writing-for-agents` names the failure mode: "**sediment**: stale layers that settle because adding feels safe and removing feels risky, until you must core down through them to find what is still live." The counter-practice is that removing a stale line from a living doc requires no ceremony and no discussion. Make that explicit in the docs README so nobody feels they need permission.

**8. Lazy creation (free).** Both `domain-modeling/SKILL.md` and `setup-matt-pocock-skills/domain.md` insist on this: "Create files lazily: only when you have something to write" and "If any of these files don't exist, **proceed silently**. Don't flag their absence; don't suggest creating them upfront." An empty template file is worse than no file: it invites filler, and filler is what rots. **This is a real tension with shipping a template**, and the resolution is in §7: ship the *rules* file for each directory, plus one worked example, not empty stubs.

---

## 7. Deliverable: proposed layout for the template

### Directory layout

```
/
├── README.md                       Human entry point: what this is, how to run it.
├── AGENTS.md                       Always-loaded agent steering. Pointers + the few real rules.
├── CLAUDE.md                       One line: `@AGENTS.md`, plus any Claude-only additions.
├── CONTEXT.md                      Domain glossary. Terms only, no implementation.
├── docs/
│   ├── README.md                   Index of what each doc is for and when to write which.
│   ├── ARCHITECTURE.md             Present-tense system map + where things live. ~1 page.
│   ├── CODING_STANDARDS.md         Conventions. Read at review time, not implementation time.
│   ├── adr/
│   │   ├── README.md               The ADR rules: when, numbering, immutability, superseding.
│   │   └── 0001-record-architecture-decisions.md   Seed ADR: the decision to keep ADRs.
│   ├── learnings/
│   │   └── README.md               The learning rules: triggers, blamelessness, format.
│   ├── guides/
│   │   └── README.md               How-to docs. One task per file, Diátaxis-checked.
│   ├── agents/                     Agent-consumed reference, reached by pointer from AGENTS.md.
│   └── research/                   Primary-source research notes (this file lives here).
└── .github/pull_request_template.md   The doc-freshness checklist gate.
```

Deliberate choices:

- **`docs/adr/` not `docs/decisions/`** — matches the installed skills. Arbitrary otherwise.
- **`CONTEXT.md` at the root, not under `docs/`** — the installed `domain-modeling` skill and `setup-matt-pocock-skills/domain.md` both look for it at the root.
- **No `CONTEXT-MAP.md`, no per-context directories** — that's the multi-context variant, warranted only in a genuine monorepo. A new project is single-context.
- **Directories ship a `README.md` and (for ADRs) one worked example, never empty stubs.** This satisfies "create lazily" while still teaching the practice on day one.
- **No `docs/tutorials/`** — a brand-new project has no users to onboard. Add it when someone needs it.

#### `docs/adr/README.md`

````markdown
# Architecture Decision Records

A record of *why* the system is the way it is. Append-only: this directory is the
one place in the repo where nothing is ever rewritten.

## When to write one

All three must be true:

1. **Hard to reverse** — changing your mind later costs something real.
2. **Surprising without context** — a future reader will ask "why on earth?"
3. **A real trade-off** — there were genuine alternatives and you picked one.

If any is missing, skip it. Easy-to-reverse decisions get reversed; unsurprising
ones raise no questions; where there was no alternative there is nothing to record.

Typical qualifiers: architectural shape, how parts integrate, technology choices
carrying lock-in, ownership and scope boundaries, deliberate deviations from the
obvious path, constraints invisible in the code, and non-obvious rejected options.

## Rules

- **Filename**: `NNNN-kebab-case-title.md`, `NNNN` = highest existing number + 1.
- **Numbers are never reused**, even if an ADR is superseded or withdrawn.
- **Immutable once accepted.** Fix typos; otherwise never edit the substance.
- **To change your mind**, write a new ADR that supersedes the old one, and add
  `superseded by ADR-NNNN` to the old one's status. Never delete an ADR.
- **`ls` is the index.** There is no hand-maintained table of contents to rot.

## Template

Copy `0001-record-architecture-decisions.md` and cut what you don't need. An ADR
can legitimately be a title and one paragraph; the value is recording *that* a
decision was made and *why*, not filling in sections.
````

#### `docs/adr/0001-record-architecture-decisions.md`

````markdown
---
status: accepted
date: YYYY-MM-DD
---

# 0001. Record architecture decisions

We will keep a numbered, append-only record of architecturally significant
decisions in `docs/adr/`, so that a future reader can tell a deliberate choice
from an accident and knows what would break if they reversed it. The alternative
— relying on commit messages and memory — fails as soon as the people change.

## Consequences

- Reversing a decision means writing a new ADR, not editing the old one.
- Anyone contradicting an existing ADR is expected to say so explicitly.
````

#### `docs/learnings/README.md`

````markdown
# Learnings

What the system taught us the hard way. Append-only and blameless: we describe
systems, assumptions and decisions, never people.

## When to write one

Any of:

1. Something broke in a way nobody predicted.
2. Work or data was lost, however briefly.
3. A fix took far longer than its size suggests — the time went into *finding* it,
   and that search is the knowledge.
4. The same mistake happened twice.
5. An assumption held by the team, or written in a doc, turned out to be false.

Skip it for bugs you understood immediately, where the fix is the whole story.

## Filename

`YYYY-MM-DD-short-slug.md`.

## Template

```
# YYYY-MM-DD — {what went wrong, in one line}

**Trigger**: {which of the five}

## What happened
{Plain narrative. Systems and timings, no names.}

## Why it happened
{The assumption that turned out to be false.}

## What we changed
{Bullets. Link ADRs, tests, standards — don't restate them.}

## The transferable lesson
{One or two sentences, stated as a rule someone could apply elsewhere.
 This is the part worth reading in a year.}
```
````

#### `docs/README.md`

````markdown
# Docs

Two kinds of document live here, with very different rules.

**Append-only records** — written once, never rewritten, free to keep:

- `adr/` — why the system is the way it is. See `adr/README.md`.
- `learnings/` — what went wrong and what it taught us. See `learnings/README.md`.
- `research/` — findings from primary sources, dated and cited.

**Living descriptions** — must track reality, so they cost maintenance forever.
Keep them short; delete stale lines without ceremony:

- `ARCHITECTURE.md` — the system as it is today. ~1 page.
- `CODING_STANDARDS.md` — conventions, applied at review time.
- `guides/` — how to perform a specific task. One task per file.

Two rules that keep this from rotting:

1. **A doc changes in the same pull request as the code that invalidated it.**
2. **If you can derive it from the code, don't write it down.** Directory listings,
   dependency lists and command lists go stale silently; the code cannot.

Create files lazily. An empty template invites filler, and filler is what rots.
````

````markdown
## Docs

- [ ] Changed a part, an interface, or where something lives → `docs/ARCHITECTURE.md` updated
- [ ] Reversed a recorded decision → a new ADR supersedes the old one
- [ ] Introduced or renamed a domain term → `CONTEXT.md` updated
- [ ] Hit one of the learning triggers → a note in `docs/learnings/`
````

## 8. Summary of recommendations

1. **Split knowledge into append-only records (ADRs, learnings, research) and living descriptions (glossary, architecture, standards, steering).** Push everything you can into the append-only side; it is free forever. Keep the living side small enough to actually stay true.
2. **ADRs**: Pocock-light format (a title and a paragraph is a valid ADR), with Nygard's hard rules — sequential numbering, numbers never reused, immutable once accepted, superseded not deleted. Live in `docs/adr/`. Gate on the three-part test. MADR's option/pros-cons sections are available but optional; MADR's full template is heavier than a new project can sustain.
3. **Architecture**: one `docs/ARCHITECTURE.md`, borrowing C4's context/containers framing (Brown himself says those two levels suffice for most teams), skipping levels 3–4, with a "where things live" table. arc42 is heavyweight and duplicates your ADR directory and glossary; skip it.
4. **Learnings**: blameless, append-only, `YYYY-MM-DD-slug.md`, five concrete triggers generalised from Google SRE's postmortem criteria. The "transferable lesson" line is the payload. Keep incident learnings separate from agent-environment retros.
5. **Human/agent split**: content in `AGENTS.md`, `CLAUDE.md` is `@AGENTS.md`. `AGENTS.md` holds pointers and the handful of rules that change behaviour — not architecture, not directory layouts (Anthropic's own trim guidance cuts exactly those). `CONTEXT.md` is a glossary and nothing else. Standards are read at review time, not implementation time.
6. **Freshness**: same-PR updates, a four-line PR checklist, CI checks only for the mechanical things (dead links, ADR number collisions, `AGENTS.md` length), aggressive deletion, and lazy creation. Google's freshness-date-plus-bot mechanism works but is heavyweight — defer it.
